# 发现计划：Karens Agent 股票分析智能体

**日期**：2026-07-02
**产品阶段**：Existing Product（karensAgent v1.1.0，新增第二个 Agent）
**发现目标**：设计一个股票分析 Agent，具备每日大盘动荡报告 + 个股深度分析能力，LLM 驱动，技能可插件化扩展，能零成本定时运行

---

## 1. 背景

karensAgent 当前只有一个 GitHub 热榜追踪 Agent（v1.1.0）。PRD 中 US10 明确规划了股票分析 Agent，路线图 Phase 2 的核心任务。

参考项目：[daily_stock_analysis](https://github.com/ZhuLinsen/daily_stock_analysis)（53k+ stars），LLM 驱动的多市场股票智能分析系统。借鉴其多 Agent 协作架构、LLM 分析引擎、技能/策略插件化设计、多渠道推送和 GitHub Actions 零成本定时方案。**但本项目自行实现，非 fork 或复制。**

### 核心理念差异

| 维度 | daily_stock_analysis | karensAgent Stock Agent |
|------|---------------------|------------------------|
| 定位 | 独立完整股票分析平台 | karensAgent 平台的第二个 Agent 插件 |
| 规模 | 全栈（FastAPI + React + Electron + Bot） | Agent 插件（复用现有平台能力） |
| 复杂度 | 多市场/多 Agent 协作/回测/持仓 | 聚焦：大盘报告 + 个股分析 |
| LLM | 10+ 模型后端适配 | 优先 Claude/DeepSeek |
| 前端 | 独立 React SPA | Vue3 页面，复用现有设计系统 |

## 4. 验证实验

### 实验 A：LLM 分析质量 PoC 🧪

| 维度 | 内容 |
|------|------|
| **验证假设** | H1（信息增量）+ H2（逻辑正确性） |
| **方法** | 手工构造 Prompt + 1 只真实 A 股行情 context（茅台 600519），调 Claude 和 DeepSeek 分别生成报告，人工评估 |
| **输入素材** | 日 K 线数据 + 技术指标（MA/MACD/RSI/量比）+ 近 3 日新闻标题 + 大盘概况 |
| **成功标准** | ① 报告中 ≥ 2 条有独立逻辑的洞察（非数据复述）② 0 处事实性错误（如把涨说成跌）③ 有明确的"不知道/不确定"表达（而非自信地胡编） |
| **失败标准** | 出现幻觉（编造不存在的新闻/数据）、分析结论与数据矛盾 |
| **工作量** | ~1 小时 |
| **时间线** | 今天/明天 |

### 实验 B：最小可行分析流程（Dogfooding）🍽️

| 维度 | 内容 |
|------|------|
| **验证假设** | H3（用户真正会使用） |
| **方法** | 写一个极简 Python 脚本：输入代码 → 调 LLM → 输出 Markdown 报告 → 手动发飞书。连续使用 3 天，记录使用频率和决策影响 |
| **成功标准** | 连续 3 天主动使用，且 ≥ 1 次因报告内容改变了操作决策（如原本想买但看了分析决定观望） |
| **失败标准** | 用了 1 天就忘了 / 觉得不如直接看同花顺 |
| **前置依赖** | 实验 A 通过（否则没东西可测） |
| **工作量** | ~2 小时 |
| **时间线** | 实验 A 通过后，3 天观察期 |

### 实验 C：技能接口最小验证 🔌

| 维度 | 内容 |
|------|------|
| **验证假设** | H4（插件化收益 > 成本） |
| **方法** | 先硬编码"技术面分析"和"消息面分析" 2 个维度 → 然后以统一接口接入第 3 个"资金面分析"，统计新增代码量 |
| **成功标准** | 第 3 个技能接入 ≤ 50 行新增代码，调度器无需修改 |
| **失败标准** | 需要改动调度逻辑或 > 100 行新增代码 |
| **前置依赖** | 实验 A + B 通过 |
| **工作量** | ~3 小时 |
| **时间线** | Week 1 |

## 5. 发现时间线

```
Day 1-2    实验 A：LLM 分析质量 PoC
              └─ 写 Prompt，调 Claude/DeepSeek，人工评估
              └─ 🛑 如失败 → 重新设计 Prompt 策略或调整预期
              
Day 3-5    实验 B：Dogfooding 最小可行流程
              └─ 极简脚本，连续 3 天使用
              └─ 🛑 如失败 → 反思使用场景，可能调整产品形态
              
Day 6-8    实验 C：技能接口验证
              └─ 2→3 技能扩展成本实验
              └─ 🛑 如失败 → 放弃插件化，硬编码方案
```

## 6. 决策框架

| 实验 | 如果成功 → | 如果失败 → |
|------|-----------|-----------|
| A: LLM 分析质量 | 进入实验 B | ① 换模型 ② 优化 Prompt ③ 缩小分析范围（只做大盘不做个股） |
| B: 用户真正使用 | 进入实验 C，启动正式开发 | ① 反思交互形态（加 Web 端？对话式？）② 可能降低为"纯推送"模式（不期望主动查询） |
| C: 技能插件化 | 正式架构设计采纳插件化方案 | 硬编码 ≤ 3 个分析维度，不做插件化过度设计 |

## 7. 参考项目启示总结

从 [daily_stock_analysis](https://github.com/ZhuLinsen/daily_stock_analysis) 中提取的可借鉴设计：

| 模块 | 借鉴点 | 本项目如何简化 |
|------|--------|--------------|
| Agent 编排 | 多 Agent 分工（technical/risk/intel/decision/portfolio） | 先只做 1 个 StockAgent，内部 skills 拆分 |
| 数据源抽象 | `data_provider/` 统一接口 + 多源 fallback | 先只接入 akshare，接口预留扩展点 |
| LLM 引擎 | LiteLLM 适配多模型后端 | 先直连 Claude/DeepSeek API |
| 策略系统 | YAML 配置 + strategy_agent 动态加载 | 先硬编码 2-3 个分析维度 |
| 通知分发 | 11 种通知渠道统一抽象 | 复用 karensAgent 现有的飞书 notifier |
| GA 定时 | `.github/workflows/00-daily-analysis.yml` | 参考其 workflow 结构 |
